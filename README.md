## The way I build

I start with the user's problem, keep the first version focused, then iterate with feedback. I care about readable code, useful documentation, and making the everyday path feel effortless.

| At the workbench | What that looks like |
| --- | --- |
| **Product thinking** | Find the smallest useful slice before adding features. |
| **Engineering** | Prefer clear boundaries, predictable behavior, and maintainable choices. |
| **Collaboration** | Share progress early, ask good questions, and leave things easier to understand. |

## Current curiosities

A few project directions I’m exploring—small enough to stay focused, useful enough to keep improving:

These are evolving ideas, not a list of shipped products. I’m interested in the useful details: good defaults, clear feedback, and a smooth path from install to “that saved me time.”
